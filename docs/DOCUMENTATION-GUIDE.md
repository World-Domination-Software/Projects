# Documentation Guide

This guide describes how we write and maintain documentation for our projects.

## Principles

- **Short paragraphs** – Keep text compact and easy to scan.
- **Clear headings** – Use headings to break up topics and make navigation easier.
- **Bullet lists** – Prefer bullet lists for steps, checklists, and key points.
- **Examples** – Include short examples or scenarios where they clarify concepts.
- **Page length** – Aim to keep each page under 500 lines; split content if it grows too large.

## Linking

- Link to related pages whenever it adds useful context.
- Use relative links within this repository (for example, `docs/bug-reporting.md`).
- In the wiki, prefer GitHub wiki links such as `[[Bug Reporting]]` and `[[Troubleshooting]]`.

## Structure for new pages

When adding a new documentation page:

1. Start with a short overview that explains the purpose of the page.
2. Add sections with headings for setup, usage, troubleshooting, and notes as needed.
3. Include at least one example or concrete scenario.
4. Link to related pages in a final "Related pages" section.
5. Add a short tags line at the bottom (for example, `Tags: documentation, troubleshooting`).

## Tone and audience

- Write for both players and developers where relevant.
- Avoid internal jargon when a simpler phrase will do.
- Be friendly but professional.

Following these guidelines will keep our documentation consistent and easy to read as it grows.
